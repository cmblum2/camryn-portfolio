Designed and built FHI Heat's SQL warehouse from zero — a dbt-style raw → staging → marts model (hundreds of tables/views) unifying ~15 source systems across the US & EU via nightly Python ETL: every commerce, ad, search, ERP, fulfillment, and marketing platform the company runs on. The single source of truth every downstream tool queries.

How it works
  • Sources (~15, US & EU) — commerce: Shopify, Amazon (Seller + Vendor Central), TikTok Shop. Ads: Amazon, TikTok, Meta, Google. Search & analytics: Google Analytics (GA4), Search Console, Merchant Center. Plus SAP B1 (ERP), ShipStation, Attentive, and Euka — each via its own API.
  • Scale & schema — a dbt-style raw → staging → marts model: ~380 tables / ~120 views across 6 schemas, tens of millions of rows (SAP invoice lines and Attentive events alone run into the millions), conformed onto shared dimensions via a cross-marketplace SKU bridge that resolves one physical product across every channel; USD/EUR normalization; nightly Python ETL.
  • Reliability & reconciliation — incremental idempotent upserts, schema-drift handling, snapshot de-duplication, and data-quality checks; cross-source reconciliation (ad spend across platforms vs. the SAP ledger, Amazon Seller vs. Vendor, GA4 vs. orders) into one revenue-and-margin view.

Read how it worksHide details

To replace a third-party creator-intelligence vendor, I built a standalone pipeline that scrapes TikTok's public creator, video, and comment data — the two things no official API returns: creators outside your own shop (for cold affiliate outreach) and raw comment text scored for buy-intent. It feeds the affiliate outreach team and the decision engine below.

How it works
  • Beating bot-detection (the core problem) — TikTok's comment/video endpoints are heavily defended; signed APIs and headless/headful Playwright all returned 'detecting a bot,' on datacenter and clean residential IPs alike. The breakthrough: the block is on the automated browser itself (navigator.webdriver + launch flags), not the IP — so I drive a genuine Chrome as a normal OS process and attach over the DevTools Protocol (CDP), letting TikTok's own JS sign the requests.
  • Robust capture — read response bodies via raw CDP (Playwright returns empty for the signed endpoints); paginate comments by scrolling the last one into view and expanding reply threads (the naive method silently capped at ~40); a fresh browser context per video so one bad video can't wedge a run (verified 250 comments in ~86s).
  • Explainable scoring & compliance — buy-intent is a transparent regex lexicon (high/med/low label + category, auditable by design — not a black box); public data only, polite pacing, and an opt-out path that deletes stored data and blocks future scraping.

② decideAffiliate ad-spend decision engine

Read how it worksHide details

The engine that told FHI's affiliate managers what to do: which creators to send product to, and which TikTok GMV Max campaign to scale, cut, or tune — grounded in real margin, guardrailed, and causally validated. A deterministic rules layer makes every call (ROAS vs. margin breakeven; creator rank vs. eligibility); an LLM only narrates the verdict and cites the evidence. Shipped and in use (a live page + a weekly one-click report). It now closes its own loop: every recommendation is archived and later graded against what actually happened, so the engine measures whether its own advice worked — then re-ranks tomorrow's actions by dollar impact.

How it works
  • Architecture — three live sources (a 138K-creator roster, the SQL warehouse, and scraped comment text) → a deterministic decision layer (plain SQL + pandas: campaign ROAS vs. margin breakeven → cut/tune/scale; creator rank + eligibility → sample) → a RAG layer that explains each verdict and cites its evidence. 'Code decides, the LLM narrates' — the 138K creators stay in SQL and JOIN at answer time; only comments are embedded (MiniLM → Chroma).
  • Two validations, not one — (1) campaign decisions: an out-of-sample backtest (recompute every verdict from pre-cutoff data, measure realized outcomes after, no look-ahead) hit 100% profitable/unprofitable classification across four cutoff windows — the 'keep' side rested on few campaigns, so I lean on the robust 'stop' side. (2) creator sampling: a matched-control difference-in-differences (each seeded creator vs. comparable un-sampled creators) gave rank↔lift Spearman ≈ −0.58, ~77% of sampled creators showing positive lift.
  • Built on evidence — the scorer was rebuilt after a backtest showed prior-GMV had ~zero forward skill (information coefficient ≈ −0.03): reframed around marginal value (efficiency, buy-intent, product affinity) with a 0-video eligibility gate (53% of 'active' creators had posted nothing). Guardrails: ordinal ranks only (never size spend), protected matched controls, epsilon-greedy exploration to de-bias the learning loop, and a drift monitor (feature PSI) that can hold a release. Whole-engine eval: 5/5.
  • Closes its own loop (self-scoring) — the engine archives each day's recommendations and later grades them against outcomes with zero look-ahead and zero manual input: a difference-in-differences check against unchanged campaigns (as control) for whether an action actually moved the number, an adoption/direction check (was the call followed?), and a daily re-validation of its own timing claims that gates alerts on sample size. Every recommended action is ranked by estimated dollar impact per month on one common scale, so the queue is prioritized by money at stake — not noise. Reported platform ROI is treated as total-channel (it claims organic + affiliate orders too) — rank with it, never size spend from it.
SQL warehouse → LangGraph decision engine → out-of-sample dollar backtest → self-scoring loop

The models are only useful if someone acts on them, so I built the alerting layer as an n8n workflow: a daily schedule fans out to four watchers — new high-intent creators in the sampling queue, campaign verdicts flipping, model drift, and the 8–14-day 'spark' window on videos — each polling the deployed engine, diffing against the last run, and alerting only when something changed.

How it works
  • A daily schedule trigger → 4 conditional branches, each hitting the deployed engine's endpoints, diffing the result against a persisted snapshot, and posting a chat alert (Slack/Discord) only on change — no alert fatigue — plus a dedicated error-handler workflow.
  • A light MLOps touch — one branch polls the deployed model's /drift health endpoint, so the same layer flags model degradation, not just business events.
  • Secrets stay out of the flow (webhook read from an env var); the public version runs against a synthetic engine, the internal twin adds a branch relaying the live /alerts.

Six-figure books reconciliation (M&A diligence)

→ 0.5% variance
six-figure discrepancy, reconciled
Data reconciliationForensic analysisSQLETL / API integrationFinancial data
Read how it worksHide details

During acquisition diligence, the buyer flagged a large apparent shipping discrepancy — the ERP showed far more paid to the postal carrier than shipping labels were actually bought for. Working solo in the warehouse, I reconciled 570K+ shipping records against the SAP payment ledger and proved it was a bookkeeping mis-classification, not missing money: shipping is prepaid through two carrier 'wallets' that were both being booked under a single vendor. Counting both wallets and both payment streams, spend matched payments to ~0.5% over three years — and the correction was booked.

How it works
  • Cross-source forensic reconciliation — the ShipStation API gives ground truth on every label bought (by carrier and prepaid wallet); the SAP ledger gives what was paid and how it was booked. I joined 'spent' vs. 'paid' month-by-month and in total across both wallets and both payment streams.
  • Root cause — one vendor code was hiding two carriers; only putting shipping ground truth next to the ERP exposed the mapping. I also traced a mid-window vendor switch that had booked some shipping as software subscriptions, and separated booking-lag timing from true variance.
  • Result — 573,866 label records over three years reconciled to a 0.97 month-to-month correlation and ~0.5% residual variance, delivered as a color-coded proof workbook (problem/solution, monthly proof, line-item evidence) an outside diligence team could follow.

Fulfilled-by-TikTok build-vs-buy analysis

a firm "no"
build-vs-buy, backed by data
Cost modelingCausal inference (natural experiment)Decision analysisSQL / API dataData viz
Read how it worksHide details

TikTok pitched its Fulfilled-by-TikTok program (they warehouse & ship your inventory at a higher fee) with claims that faster shipping converts better and gets more traffic. Instead of trusting the brochure, I priced every fee and every claim against FHI's actual first-party data and recommended against blanket adoption — with a per-SKU strategy: don't convert the light-weight brushes (~95% of volume, structurally costlier under FBT), pilot the heavy tools where FBT actually saves, and make TikTok underwrite the unverifiable 'free traffic' claim. Delivered as an interactive dashboard for a non-technical decision-maker.

How it works
  • Per-SKU rate-card simulation — priced 11,593 fee-bearing orders individually (each against its real ShipStation weight and the exact FBT tier table), not a blended average that would hide FBT saving on heavy items but losing on light ones. FBT beat the in-house label on only ~16% of orders.
  • Robustness — TikTok revised the rate card twice mid-analysis; I verified each change only touched 16–50 lb / multi-unit tiers, proving every FHI-relevant tier (≤5 lb) was unchanged, so the verdict survived both revisions.
  • Causal check on the claims — a fast-vs-slow delivery-state natural experiment showed customers didn't punish slower shipping (repeat rate moved ~0.2 pts across a 3.7→6.0-day spread), and I priced the 'free traffic' claim against real ad CAC to reframe it as a concession to extract.
per-SKU rate-card simulation → natural experiment on shipping speed → recommend NO → cost avoided

The executive BI web app FHI's CEO and operators ran on — daily revenue, margin, channel, inventory, and ad views where every panel ends in a ranked 'Actions' band (cut / fix / scale / watch) plus an alert layer (stockouts, ROAS collapse, creator decay). It reframed the dashboard from display to decision, and surfaced what the DTC-only reports missed: a major wholesale channel, and a large slice of ad spend with no measurable attribution.

How it works
  • Next.js 15 (App Router) over the MSSQL warehouse, panels built only on the marts layer. A cross-channel 'Product 360' rolls one physical product across Amazon, Shopify, TikTok, SAP wholesale, inventory, and ads via the canonical SKU bridge.
  • Performance — heavy views (a ~3.6M-row SAP scan ran ~45s cold) made instant with a two-level cache (server + browser), a global mutex so heavy queries never run concurrently, warm-on-boot + background refresh, and deadlock auto-retry.
  • Production ops — bcrypt + signed-cookie auth with per-IP lockout, and a Windows push-to-live deploy pipeline (robocopy mirror, next build with automatic .next-prev rollback on failure, behind a Cloudflare Tunnel) at ~80s per cycle over ~400 commits.
  • Data-quality — caught a bug where a marketplace's intraday API snapshots were fanning out as duplicate sales (inflating that channel's revenue) and rebuilt the metric from deduplicated source.

SteMy is a hands-free voice AI lab partner for stem-cell researchers. Turning stem cells into heart cells is notoriously irreproducible batch-to-batch — and researchers are hands-busy at the hood during time-sensitive windows, with dozens of variables to track. I build and lead the voice-interaction layer that lets them capture and recall the right experimental variable at the right moment, hands-free. A separate, ongoing UW–Madison research engagement with the People and Robots Lab (Prof. Bilge Mutlu) × the Kamp Lab (Dr. Timothy Kamp); part of an active NIH R01 that scored highly — funding anticipated.

How it works
  • Domain-tuned voice UX — protocol- and study-day-aware (it prompts for the variables that matter at that differentiation stage), with lab-reality speech: biology-vocabulary biasing, number normalization, anaphora memory ('that replicate'), hands-free wake-phrase + barge-in, and confidence-gated auto-execute with a clarification fallback.
  • Architecture — full-stack (React 18 + Vite / Python + FastAPI + SQLite); real-time voice via OpenAI's Realtime API over a persistent WebRTC session (~600–900ms), with server-mediated tools: ephemeral session tokens, a per-page tool catalog, and one executor enforcing auth + telemetry. Migrated from a ~1.8–3s turn-based pipeline without a rewrite; the hard state lives in the backend (slot-filling, a navigate_to tool) so the LLM has one narrow job per turn.
  • Safety & shipping — a spoken confirmation gate before any action that changes an experiment record; shipped in phases behind a runtime feature flag (roll back from the browser, no redeploy), covered by Vitest + HTTP smoke-test suites that caught a stale-session bug pre-release.
  • Scope & funding — I build and lead the voice/tools layer; teammates build the agent and the reproducibility 'brain.' Co-author on the methods paper; part of an active NIH R01 that scored highly (funding anticipated).
