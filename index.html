The foundation — built from scratch

The data warehouse the whole business ran on.

5 sources → 1
unified warehouse, built from scratch

This is the foundation everything else stands on. At FHI Heat I built a multi-platform data warehouse from scratch in SQL, pulling five siloed systems — the ERP, the Amazon and TikTok Shop marketplaces, the Shopify DTC store, and the shipping carrier — into one place, refreshed by nightly Python jobs. Before it, every question meant stitching exports together by hand. After, the whole team could query sales, margin, inventory, and fulfillment from a single source of truth — and every project to the right of it on the graph is something I built on top.

How it works
  • Ingestion: nightly Python jobs pulling Amazon SP-API, TikTok Shop API, Shopify Admin/GraphQL, the ERP, and the shipping carrier — each with its own schema, IDs, and currencies.
  • Modeling: normalized the sources into a unified dimensional schema (order and line-item facts; product, channel, and date dimensions) with cross-marketplace SKU mapping.
  • Reliability: incremental, idempotent upserts, schema-drift handling, and de-duplication of intraday API snapshots so the same sale is never double-counted.
ERP + Amazon + TikTok Shop + Shopify + shipping → nightly Python ingestion → one SQL warehouse
the sale · finance

I reconciled a six-figure books discrepancy to 0.5%.

→ 0.5% variance
six-figure discrepancy, reconciled

Leadership flagged a large payment to a shipping carrier — a six-figure sum with no matching shipping labels, which looked like it could be missing money. I loaded 570K+ shipping records into the warehouse and reconciled them line-by-line against the ERP payment ledger. The cause turned out to be a bookkeeping mis-classification: two prepaid carrier wallets had both been booked under a single vendor. Counting both, the spend matched payments to within ~0.5% — nothing was missing, and the correction was booked.

How it works
  • Reconciled 570K+ shipping records against the ERP payment ledger with SQL joins and aggregation.
  • Root-caused the gap to a many-to-one vendor mapping — two prepaid carrier wallets booked under one vendor.
  • Three-year variance analysis brought spend vs payments to within ~0.5%, proving a bookkeeping mis-classification, not missing money.
570K shipping records → reconciled vs ERP ledger → six-figure gap → bookkeeping fix

A build-vs-buy call I won by saying no.

a firm "no"
build-vs-buy, backed by data

TikTok pitched its Fulfilled-by-TikTok program. Instead of guessing, I simulated the exact rate card per-SKU across thousands of real orders, and ran a natural experiment showing customers didn't actually punish slower shipping. The numbers said don't switch — so I recommended against it, avoiding a five-figure annual cost. The harder part was making the case that the default 'yes' was the wrong one.

How it works
  • Simulated the carrier's exact rate card per-SKU (weight and dimensional-weight tiers) across thousands of historical orders from the warehouse.
  • Ran a natural experiment across shipping-speed cohorts — no measurable penalty in customer behavior for slower shipping.
  • Framed it as build-vs-buy: in-house fulfillment cost vs the program's per-order economics → recommend against switching.
per-SKU rate-card simulation → natural experiment on shipping speed → recommend NO → cost avoided
affiliate growth engine

The affiliate ML system that found who to actually pay.

buy-intent ranked
creator-discovery ML system

To grow the affiliate program you first have to find the right creators. I built a resilient TikTok scraper that mines public comment data at scale (rotating strategies so it keeps working past bot-blocking), then a machine-learning model that scores each creator's buy-intent from that comment signal. Instead of guessing who to recruit, outreach could target the highest-intent prospects first — the discovery layer that feeds the whole affiliate pipeline.

How it works
  • Resilient scraper for public TikTok comments: rotating request strategies, pacing, and retry/backoff to survive bot-blocking, with pagination and de-duplication.
  • Feature-engineered buy-intent signals from comment text (purchase-intent language, engagement).
  • A supervised ML model scores each creator's buy-intent; creators are ranked so outreach hits the highest-intent prospects first.
scrape public TikTok comments (bot-resilient) → buy-intent ML scorer → ranked creator prospects → outreach

An ad-spend decision engine that proved its own calls.

100% OOS
out-of-sample decision accuracy

Once creators were live, affiliate ad spend was scattered across dozens of TikTok campaigns with no read on which were actually profitable after margin. I built a decision engine — LangGraph + Claude over the SQL warehouse — that scores each campaign against its own margin breakeven and returns a verdict: scale, tune, or cut. Then I backtested it out of sample: recompute every verdict from data before a cutoff date, then check what actually happened after (no look-ahead). Across four cutoff windows it hit 100% profitable/unprofitable accuracy — every campaign it flagged to stop was genuinely below breakeven, and the ones it called healthy were solidly profitable. (Honest caveat: the 'keep' side rested on few campaigns, so I lean on the robust 'stop' side.) A public, synthetic-data rebuild is linked below.

How it works
  • LangGraph state-machine agent over the SQL warehouse; a deterministic function computes each campaign's ROAS against its margin-derived breakeven (contribution margin minus commission) — code decides, the LLM only narrates.
  • Out-of-sample backtest: a temporal split decides from pre-cutoff data and scores realized post-cutoff outcomes with no look-ahead, running the exact live decision function.
  • Evaluated across four cutoff windows → 100% profitable/unprofitable classification accuracy.
SQL warehouse → LangGraph decision engine → out-of-sample dollar backtest

A no-code watchdog on the affiliate system.

auto-alerts
no-code automation (n8n)

The ML outputs are only useful if someone acts on them. I built an n8n workflow that runs on a schedule, watches the affiliate system for changes — new high-intent creators surfaced, campaign verdicts flipping, metric drift — diffs each run against the last, and posts an alert to Slack only when something actually changed. Low-code glue that turns the models' output into action without anyone babysitting a dashboard.

How it works
  • Scheduled n8n workflow queries the current state, diffs it against the last run's stored snapshot, and alerts only on change (no alert fatigue).
  • Conditional branches post formatted Slack alerts for new high-intent creators, flipped campaign verdicts, or metric drift.
  • Stateful, idempotent glue that turns model output into action with no dashboard-watching.
scheduled trigger → diff vs last run → alert on change → Slack

exec BI dashboard (Next.js)

I built the executive BI dashboard — Next.js on top of the warehouse — that leadership used for daily revenue, margin, and channel views. While building it I caught a data bug nobody had noticed: an upstream table was counting each intraday API snapshot as a separate sale, which would have overstated a channel's revenue. I traced it and rebuilt the metric from deduplicated source data. The same dashboard also surfaced a major revenue channel that DTC-only reports had been missing.

How it works
  • Next.js/React app over the warehouse with server-side data fetching — daily revenue, margin, and channel views for leadership.
  • Caught a data-quality bug via anomaly investigation: intraday API snapshots were being counted as separate sales, overstating a channel's revenue — rebuilt the metric from de-duplicated source data.
  • Surfaced a major revenue channel that DTC-only reports had been ignoring.
warehouse → Next.js exec dashboard → caught an upstream revenue-inflation bug

Ask-Your-Warehouse: plain English → governed SQL.

5 roles
governed NL→SQL agent · live

This is a public, shareable rebuild modeled on my own warehouse — same schema and roles, synthetic data — so the skill is visible without exposing anything private. A LangGraph agent turns a plain-English question into SQL, runs it, and answers with a chart, with real guardrails (not just prompts): it only writes read-only SELECTs, self-repairs when a query errors, and enforces role-based access at three layers — a CEO sees everything, an intern sees no dollar amounts. Ask it to 'delete all orders' and it refuses. Five role logins in the live demo.

How it works
  • LangGraph agent: NL → SQL → execute → chart, with a guardrail node (read-only SELECT only, forced LIMIT, blocks DML) and a self-repair loop (catch SQL error → feed it back → retry).
  • Role-based access in three layers: a schema-scoped prompt, a guard that rejects out-of-scope columns, and per-role DuckDB views as a physical backstop (hidden columns literally absent).
  • DuckDB engine, Streamlit UI, and an evaluation harness — on synthetic data modeled on my real warehouse schema.
plain-English question → LangGraph → guardrailed read-only SQL → chart + answer, or a refusal
